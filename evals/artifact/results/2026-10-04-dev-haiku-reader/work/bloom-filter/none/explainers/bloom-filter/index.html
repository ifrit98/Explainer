Bloom filters: answering "have I seen this before?" with very little memory

A Bloom filter is a row of bits plus a few hash functions. It can tell you that something is definitely new or probably seen before. It uses a small, fixed amount of memory no matter how long the items are. The cost is that the "probably" answer is sometimes wrong. This page shows how it works, lets you try one, and explains how to work out how often it will be wrong.

1. The problem

Lots of programs need to ask the same question over and over: is this item in my set? Has this user name been taken? Has the web crawler already visited this URL? Is the row I'm looking for in this file on disk, or should I skip the file?

The obvious answer is to store every item, say in a hash set, and look it up. That gives exact answers, but you pay for the items themselves. A billion URLs of about 60 bytes each comes to roughly 60 GB before any overhead. Often you can't afford that much fast memory, or the full set lives somewhere slow (on disk, across the network), and you just want a cheap check before you go there.

A Bloom filter gives up a little accuracy in return for a large saving in memory. At a 1% error rate it needs about 10 bits per item, whether the item is a 6-letter word or a 2 KB document. For those billion URLs that's about 1.2 GB.

2. The machinery: bits and hash functions

You need two ingredients:

  • An array of m bits, all starting at 0.
  • k different hash functions. A hash function turns any input (such as a string) into a number that looks random but is always the same for the same input. We take each number modulo m, so it picks a position in the array.

So each item is linked to k positions in the array. You can think of them as the item's "fingerprint" of bit positions.

Add an item: compute its k positions and set all of those bits to 1. (If a bit is already 1, it stays 1.)

Check an item: compute its k positions and look at the bits.

  • If any of them is 0, the item was definitely never added. Adding it would have set that bit to 1, and bits never go back to 0.
  • If all of them are 1, the item was probably added. Those bits might have been set by other items.

The filter never stores the item itself. It only stores the bits that items have switched on. That's why it's small, and also why it can be fooled.

Things to notice:

  • A word you added always comes back "probably yes". There are no false negatives.
  • When the filter is nearly empty, most new words land on at least one 0 and are rejected straight away.
  • As you add more words, the array fills up with 1s. Eventually a word you never added lands only on 1s that other words set, and the filter says "probably yes". That's a false positive. The Hunt button tries made-up words until it finds one.
  • Different words sometimes share positions. That sharing is what lets the filter use so few bits, and it's also the cause of false positives.

4. How it can be wrong

There are four possible outcomes:

Filter says "definitely not"Filter says "probably yes"
Item was addedImpossible: its bits were set to 1 and never clearedCorrect
Item was not addedCorrectFalse positive: other items happened to cover all its bits

So the error only goes one way. "No" is always trustworthy, and "yes" means "check properly if it matters". That fits the usual way Bloom filters are used, as a cheap guard in front of an expensive exact lookup:

  • A database keeps a Bloom filter for each file on disk. Before reading a file to look for a key, it asks the filter. "Definitely not" saves a disk read. "Probably yes" means it reads the file, and now and then finds nothing there, which costs a wasted read but never gives a wrong answer.
  • A web cache only stores a page the second time it's requested. A Bloom filter of "URLs seen once" answers "have I seen this before?" cheaply, and the occasional false positive just means a page gets cached a little early.

Two more limits come from the same design:

  • You can't delete. Setting an item's bits back to 0 might erase bits that other items also depend on, and then those items would get false negatives. (A variant called a counting Bloom filter stores a small counter in each slot instead of a single bit. Adding increments the counters and deleting decrements them, at several times the memory cost.)
  • You can't list the contents. The items themselves were never stored, only bits.

5. How often is it wrong? The arithmetic

Here's how to estimate the false positive rate. Assume the hash functions behave like independent, fair random choices of position. Real hash functions are close enough to this.

Step 1: chance that a particular bit is still 0. A single hash picks a particular bit with probability 1/m, so it misses that bit with probability 1 − 1/m. Adding n items performs kn hashes in total, and the bit stays 0 only if every one of them misses it:

P(bit still 0) = (1 − 1/m)kn ≈ e−kn/m

(The approximation uses the standard fact that (1 − 1/m)m ≈ 1/e when m is large.)

Step 2: chance of a false positive. Now check an item that was never added. Its k positions are effectively random, and each one is 1 with probability 1 − e−kn/m. The filter wrongly says "yes" only if all k are 1:

p ≈ (1 − e−kn/m)k

Put another way, if a fraction f of the bits are 1, the false positive rate is about fk. The demo above shows this estimate under the bit array.

Step 3: choosing k. The number of hash functions pulls in two directions:

  • More hashes per check means a stranger has to get lucky more times, which lowers the error.
  • More hashes per insertion fills the array with 1s faster, which raises the error.

The best balance turns out to be when about half the bits are 1. That happens when

k = (m/n) · ln 2 ≈ 0.69 · (m/n)

With that choice, each extra hash halves the error, so p ≈ (1/2)k. Rearranging gives the number of bits needed per item for a target error rate p:

m/n = −ln p / (ln 2)2 ≈ 1.44 · log2(1/p)

6. Explore the trade-off

Move the sliders to see how memory per item (m/n) and the number of hashes (k) affect the false positive rate. The curve plots the rate against k for the chosen memory budget. Its lowest point is the best k.

Try overfilling the filter: keep k fixed and slide the bits per item down. This is what happens when you build a filter for a million items and then put ten million in it. The error rate doesn't creep up slowly; it rises steeply toward 100% as the array fills with 1s. Bloom filters need to be sized for the largest number of items you expect.

7. Summary

  • A Bloom filter is m bits plus k hash functions. Adding an item sets its k bits. Checking an item tests them.
  • Any 0 means definitely not seen. All 1s means probably seen.
  • It can be wrong in only one direction: false positives, which happen when other items have already set all of a new item's bits. False negatives can't happen.
  • The false positive rate is about (1 − e−kn/m)k. With the best k, about 10 bits per item gives 1%, and every extra ~4.8 bits per item cuts the rate tenfold.
  • It saves memory because it stores no items, which is also why it can't delete items or list them.
